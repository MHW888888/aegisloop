# Codex App Server Roadmap

AegisLoop's long-term role is a local policy, recovery, and audit layer for explicit Codex execution.

## v0.3.18 boundary

The current release keeps the CLI transport but stops treating plain stdout as the preferred protocol. It adds structured JSONL events, a result schema, a persistent job journal, and fail-closed crash recovery.

## v0.4.0 target

The next transport adapter should use Codex App Server for:

- thread start, resume, and fork;
- turn lifecycle and cancellation;
- command, file-change, MCP, and plan events;
- native approval requests;
- sandbox and approval policy configuration;
- instruction-source visibility;
- streaming progress and session health.

AegisLoop should continue to own:

- ChatGPT conversation to Codex thread binding;
- explicit arm and one-tab leader control;
- Run Capsule policy;
- local approval UI;
- result delivery and recovery;
- audit and sanitized debug snapshots.

App Server work should land as a separate adapter. It must not remove the tested CLI adapter until migration, cancellation, approval, and recovery fixtures pass on Windows, macOS, and Linux.

## Protocol compatibility guard

The first App Server adapter should use the default `stdio://` JSONL transport. The official WebSocket transport remains experimental and unsupported for production workloads. AegisLoop must not expose a non-loopback listener, and any future remote transport must require TLS plus App Server authentication.

Each connection must complete the official `initialize` request and `initialized` notification before starting or resuming a thread. AegisLoop should then use `thread/start` or `thread/resume`, followed by `turn/start`, and treat `turn/completed`, `turn/interrupt`, and streamed item notifications as the execution lifecycle source of truth.

App Server schemas are generated by the installed Codex version. Before enabling the adapter, AegisLoop must:

1. probe `codex app-server --help`;
2. require `stdio://` transport and `generate-json-schema` support;
3. generate or load schemas for the exact detected Codex version;
4. reject incompatible cached schemas instead of guessing fields;
5. keep authentication data and App Server account methods server-side, never in the browser extension or local UI JavaScript.

Recent Codex CLI builds may also expose `app-server daemon` and `app-server proxy`. `npm run doctor` reports those commands as migration signals only. Their presence does not enable an App Server adapter, prove protocol compatibility, or permit AegisLoop to skip the `initialize` / `initialized` handshake and version-matched schema checks above.

The first adapter must stay on the stable protocol surface by default. Experimental methods or fields require an explicit `experimentalApi` capability, separate fixtures, and a documented fallback. Thread goals, loaded instruction sources, model-switch warnings, and other App Server metadata should be consumed from protocol responses rather than inferred from prompts or browser labels.

If a future WebSocket adapter receives the official overloaded response (`-32001`), retries must use exponential backoff with jitter and must not replay a turn that may have produced side effects.
